❓ QUESTION:
  What are the two knob set generators currently supported by RapidFire AI for creating multi-config specifications?

✓ REFERENCE ANSWER:
  RapidFire AI currently supports two knob set generators: List() for a discrete set of values and Range() for sampling from a continuous value interval. List() takes a list of discrete values where all values must be the same Python data type. Range() takes a start, end, and dtype parameter (either 'int' or 'float') and performs uniform sampling within the given interval.

❓ QUESTION:
  How does RapidFire AI's adaptive execution engine differ from traditional sequential execution for multi-config experiments?

✓ REFERENCE ANSWER:
  Traditional tools force you to run one config after another sequentially. In contrast, RapidFire AI's adaptive execution engine shards the dataset randomly into chunks and schedules all runs on one shard at a time, then cycles through all shards. This enables interruptible execution across GPUs/CPUs, providing a far more concurrent learning experience by automatically swapping adapters and base models across GPUs and DRAM via efficient shared memory-based caching mechanisms. The swapping overhead is minimal, less than 5% of runtime. This means before the third model config even starts in the sequential approach, RapidFire AI already shows learning behaviors of all configs on the first 2-3 chunks.

❓ QUESTION:
  What is the difference between RFGridSearch and RFRandomSearch in terms of how they handle knob values?

✓ REFERENCE ANSWER:
  RFGridSearch requires each knob to have either a single value or a List() of values, but no knob should have a Range() of values or it will error out. RFRandomSearch allows each knob to have a single value, a List() of values, or a Range() of values. Its sampling semantics are independently-identically-distributed (IID): it uniformly randomly picks a value from each discrete set and from each continuous set to construct one knob combination, then repeats this process to accumulate num_runs distinct combinations.

❓ QUESTION:
  What are the four Interactive Control (IC) Operations supported by RapidFire AI?

✓ REFERENCE ANSWER:
  RapidFire AI supports four IC Ops: (1) Stop - earmarks a run to be stopped at the end of its current chunk, keeping it alive but not using GPU resources from the next chunk; (2) Resume - applicable only to previously stopped runs, earmarks them to be resumed from the next chunk onward; (3) Clone-Modify - allows adding clones of a chosen parent run with editable config knobs, optionally warm-starting with the parent's weights; (4) Delete - earmarks a run to be deleted from the next chunk onward, making its curves vanish from the plots, though model checkpoints are preserved in the experiment artifacts.

❓ QUESTION:
  What does the preprocess_fn function do in the run_evals pipeline, and what arguments does the system inject into it?

✓ REFERENCE ANSWER:
  The preprocess_fn is a mandatory user-provided function that prepares the inputs to be given to the generator model. It is invoked for each batch during the evaluation process before generation. The system injects three arguments: (1) batch - a dictionary with a batch of examples with dataset field names as keys and lists as values; (2) rag - an RFLangChainRagSpec object for document chunk retrieval and context serialization; (3) prompt_manager - an RFPromptManager object for handling instructions and few-shot examples. The function must return a dictionary with a reserved key 'prompts' containing the fully formatted prompts for the generator.

❓ QUESTION:
  What three vector store backends does RapidFire AI support and what modes of operation do they offer?

✓ REFERENCE ANSWER:
  RapidFire AI supports three vector store backends: (1) FAISS - an in-memory store that is the default and requires no setup, but only supports Create mode since it is not persistent; (2) PGVector (PostgreSQL) - a persistent vector store that supports Create, Read, and Update modes; (3) Pinecone - a cloud-hosted persistent vector store that also supports Create, Read, and Update modes. In Read mode, you retrieve from a pre-existing index. In Update mode, you add new content to an existing index. Using PGVector or Pinecone in Read mode is especially useful for efficient experimentation since you preprocess and embed your corpus once and then run many retrieval/generation configurations against the same index.

❓ QUESTION:
  What is online aggregation in the context of RapidFire AI evals, and what three confidence interval strategies does it support?

✓ REFERENCE ANSWER:
  Online aggregation is a technique adapted from database systems research that provides running metric estimates with confidence intervals in real time as shards of the evaluation dataset are processed. This enables stopping poor configs earlier and cloning better configs on the fly. RapidFire AI supports three confidence interval strategies: (1) Normal Approximation - the default strategy using the Central Limit Theorem, suitable for non-trivial sample sizes (n > 30); (2) Wilson Score - better for small sample sizes or metrics near 0/1 boundaries, more robust for extreme proportions; (3) Hoeffding Bounds - best for maximum safety with guaranteed coverage, making no distributional assumptions but producing typically loose intervals. All three support optional Finite Population Correction (FPC).

❓ QUESTION:
  What is the purpose of the accumulate_metrics_fn in the evals pipeline, and what happens if it is not provided?

✓ REFERENCE ANSWER:
  The accumulate_metrics_fn is an optional user-provided function that aggregates algebraic eval metrics across all batches of data. It is invoked once at the very end of the evaluation process after all batches have been processed. If this function is not provided, all metrics returned by the compute_metrics_fn will be assumed to be distributive (i.e., summed across batches) by default. This function is needed when metrics require weighted averaging or other custom dataset-wide aggregation logic. The return dictionary can include optional keys 'is_algebraic', 'is_distributive', and 'value_range' to support online aggregation.

❓ QUESTION:
  How does RFPromptManager select few-shot examples for each input query?

✓ REFERENCE ANSWER:
  RFPromptManager provides semantic similarity-based example selection to construct prompts with the most relevant examples for each input query. It uses an embedding_cfg to compute semantic similarity between examples and queries, where the embedding class (such as HuggingFaceEmbeddings or OpenAIEmbeddings) is specified as a dictionary with the class itself as value (not an instance). The example_selector_cls parameter determines the selection strategy - either SemanticSimilarityExampleSelector for pure similarity or MaxMarginalRelevanceExampleSelector for diversity. The k parameter controls how many examples to retrieve per query (default 3). Each example is formatted using an example_prompt_template with placeholders matching the keys in the example dictionaries.

❓ QUESTION:
  How do reward functions work in RapidFire AI for GRPO training, and what arguments does TRL inject into them?

✓ REFERENCE ANSWER:
  Reward functions are user-provided functions needed for GRPO that evaluate generated outputs during training. TRL injects lists of prompts, completions, completion IDs, and trainer state as keyword arguments. Users can use only a subset of these in their reward function signature as long as they include **kwargs. Depending on the dataset format, prompts and completions will be either lists of strings (standard format) or lists of message dictionaries (conversational format). The return type must be a list of floats (one per completion), or None for examples where the reward function is not applicable. Multiple reward functions can be passed as a list to the reward_funcs argument of RFModelConfig, and multiple variants of these lists can be used as a List for multi-config specification.

❓ QUESTION:
  What is a 'leaf config' in RapidFire AI terminology, and how does it relate to runs?

✓ REFERENCE ANSWER:
  A leaf config is a single combination of knob values in a config dictionary. In a config dictionary, a knob's value can be a singleton or set-valued (using List or Range). When set-valued knobs are fed to a config-group generator method, each unique combination produced is called a leaf config. RapidFire AI instantiates one run per leaf config, and its values are injected via the model_config argument to the user's create_model_fn() function. A run is a central concept representing this single combination of configuration knob values, and RapidFire AI assigns each run a unique integer run_id within an experiment.

  What is the recommended approach if you run out of storage space while experimenting with many LLMs?

✓ REFERENCE ANSWER:
  If you run out of storage space, RapidFire AI recommends clearing out the '.cache' folder on your home directory, which is created by Hugging Face to import base models. ❓ QUESTION:
  Why does RapidFire AI argue that simply downsampling the evaluation data is insufficient compared to its online aggregation approach?

✓ REFERENCE ANSWER:
  RapidFire AI identifies several disadvantages of downsampling alone: (1) you must decide a downsample size upfront, which is non-trivial if eval metrics have high variance across examples; (2) a single downsample introduces variance from one static snapshot, potentially leading to wrong conclusions, especially with overfitting-prone LLMs; (3) point estimates without confidence intervals can give false confidence; (4) manual resampling adds grunt work of juggling separate samples and files; (5) it requires manual checkpoint management; (6) downsampling alone does not offer dynamic control (stop, resume, clone-modify) or automated parallelization to try new configs on the fly. However, downsampling is complementary to rapid experimentation - users can use both together, as the adaptive execution engine operates on downsampled datasets all the same.

❓ QUESTION:
  How do you resolve an ImportError for GenerationMixin that occurs between experiments?

✓ REFERENCE ANSWER:
  This ImportError ('cannot import name GenerationMixin from transformers.generation') is caused by stray Python processes from the previous experiment not ending properly. To resolve it: (1) run the command 'ps -ef | grep python' and look for 'multiprocessing.spawn' or 'defunct' processes, then kill them with 'kill -9 [PID]'; (2) wait for about 2 minutes regardless of whether there were processes to kill; (3) restart the kernel and then proceed with your new experiment.

❓ QUESTION:
  What is the difference between distributive and algebraic metrics in RapidFire AI's online aggregation for evals?

✓ REFERENCE ANSWER:
  Distributive metrics are purely additive over a given set of data points, such as count of correct predictions or sum of output token lengths across queries. Algebraic metrics are averages or proportions over a given set of data points that can be decomposed into components that are individually distributive, such as precision (which divides correct predictions by total data points) or mean rouge-1 (which averages per-example values). When defining eval metrics via compute_metrics_fn and accumulate_metrics_fn, users must specify their type (algebraic or distributive) and value range for online aggregation. Metrics without a type defined are displayed as-is without projected estimates or confidence intervals.
